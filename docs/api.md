# Contrat d'API

Base : `/api/v1`, JSON, UTF-8. Authentification `Authorization: Bearer <jwt>` sauf mention. Erreurs : `{ "error": { "code": "string", "message": "string" } }` avec statuts HTTP standards. Les schémas Zod dans `backend/src/modules/*/schema.ts` font foi pour les corps ; ce document fixe les routes et règles. La spécification OpenAPI est générée depuis les schémas Zod et publiée sur `/docs` en développement (`NODE_ENV=development`).

## Auth (sans JWT)
- `POST /auth/signup/request-code` `{ universityEmail }` → `202` : envoie le code de confirmation (6 chiffres, 10 min, usage unique, 5 essais). Domaines autorisés : `app_settings.auth.allowedEmailDomains`. Réponse identique si le compte existe déjà (un mail « tu as déjà un compte » part à la place du code). `429 code_cooldown` si un code a été demandé il y a moins d'une minute.
- `POST /auth/signup/verify` `{ universityEmail, code, firstName, lastName, password }` → `201` jetons : crée le compte vérifié, rattaché au campus pilote. `400 code_invalid` (faux, expiré, déjà utilisé ou bloqué), `409 account_exists`.
- `POST /auth/login` `{ universityEmail, password }` → `200` jetons ; `401 invalid_credentials` identique que le compte existe ou non. `429 login_locked` après `auth.loginMaxFailures` échecs en `auth.loginLockMinutes` pour une adresse depuis une même IP (blocage de cette IP seulement), ou `auth.loginDailyMaxFailures` échecs sur une journée pour l'adresse (attaque répartie). `request-code` : `429 code_daily_limit` au-delà de `auth.signupCodesPerDay` codes par adresse. (`/auth/login/google` et `/auth/login/apple` : v1.1.)
- `POST /auth/refresh` `{ refreshToken }` → `200` nouveaux jetons. Chaque refresh token ne sert qu'une fois ; présenter un jeton déjà échangé révoque toute la session (`401 invalid_refresh_token`).
- `POST /auth/logout` `{ refreshToken }` → `204` : révoque la session.
- Jetons : `{ accessToken, refreshToken, accessTokenExpiresIn }` ; JWT d'accès HS256 de 15 min, refresh opaque de 30 jours.
- Limites de débit par IP : envoi de code 5/15 min, vérification et connexion 10/15 min, refresh et logout 30/min (`429 rate_limited`).

## Profil
- `GET /me` : profil privé (`home` avec adresse, coordonnées et secteur, `vehicle`, `roleMode`, `onboarding: { steps, nextStep, completed }`, `discoveryMode` tant que l'adresse ou le campus manque, `pausedToday`).
- `PATCH /me` `{ firstName?, lastName? }` ; le mail n'est pas modifiable.
- `GET /me/export` → `200` JSON en pièce jointe (`uni-moov-mes-donnees.json`) : profil, véhicule, pauses, agenda (fournisseur et dates, jamais le lien), semaine type et créneaux, trajets, portefeuille (solde, écritures, recharges, retraits), paiements, notes données et reçues (sans l'identité de qui note), événements de fiabilité, litiges, signalements, messages envoyés, appareils (plateforme, sans le jeton), préférences de notification. Aucun mot de passe, jeton ni donnée d'une autre personne. 5 par heure.
- `DELETE /me` `{ password }` → `204` : suppression définitive (docs/rgpd.md). `401 invalid_password`, `409 ride_in_progress` pendant un trajet en cours, `409 wallet_not_empty` tant que le solde n'est pas nul. Les trajets à venir sont libérés comme une annulation (les autres sont prévenus et relancés) ; nom, mail, adresse, véhicule, agenda, appareils, sessions et messages sont effacés ; trajets passés, paiements, notes et registre restent rattachés à un « Ancien membre » anonyme. Sessions et sockets fermés aussitôt ; l'adresse universitaire peut servir à une nouvelle inscription. 5 par 15 min.
- `PUT /me/address` `{ address }` : géocode côté serveur, calcule `home_sector` ; `422 address_not_found`, `503 geocoding_unavailable`.
- `PUT /me/vehicle` `{ consumptionLPer100km, defaultSeats, maxDetourMinutes }` (un seul véhicule), `DELETE /me/vehicle` (repasse en `always_passenger`).
- `PATCH /me/preferences` `{ roleMode?, defaultNavApp? }` : `auto` et `always_driver` exigent un véhicule (`409 vehicle_required`). Détour max : dans le véhicule ; notifications : M6.
- `PUT /me/onboarding/{step}` `{ status: "done" | "skipped" }`, étapes `profile`, `vehicle`, `preferences`, `calendar` : l'app reprend à `onboarding.nextStep`.
- `GET /me/pauses`, `POST /me/pauses` `{ startsOn, endsOn, recurrence, repeatUntil }`, `DELETE /me/pauses/{id}` (404 si la pause n'appartient pas à l'utilisateur). Comme un événement d'agenda : la première pause va de `startsOn` à `endsOn` ; `recurrence` la répète jusqu'à `repeatUntil` (obligatoire avec une récurrence) : `null` (une seule fois), `"weekly:N"` (toutes les N semaines, 1 à 8 ; la première pause tient dans 7 × N jours), `"monthly:N"` (tous les N mois, 1 à 6, même jour du mois ; 28 jours au plus), `"days:1,3"` (chaque semaine, les jours ISO donnés, 1 = lundi). Un an au plus du début à la fin. `400 invalid_pause` sinon.
- `GET /addresses?q=` (3 caractères au moins, 120 par heure) → `{ suggestions: [{ label }] }` : adresses existantes proposées pendant la saisie (Base Adresse Nationale, autocomplétion, proches du campus) ; l'app envoie ensuite le libellé choisi à `PUT /me/address`.
- `GET /users/{id}/public` : prénom, photo, score uniquement.

## Agenda
- `POST /calendar/connections` `{ provider: "ics", url, consent: true }` → `201` `{ connection, changedDays }` : le lien (ICS ou `webcal://`) est lu tout de suite ; `400 calendar_url_invalid` (HTTPS sur le port 443 uniquement, aucune adresse interne), `422 calendar_unreachable` ou `calendar_invalid` ; rien n'est enregistré en cas d'échec. Le lien est chiffré en base et n'est jamais renvoyé. Une seule connexion par utilisateur. CalDAV : via le lien d'abonnement ICS que les serveurs CalDAV publient ; Google et Microsoft : v1.1.
- `GET /calendar/connections` → `{ connection: { id, provider, consentedAt, lastSyncedAt, lastError } | null }`.
- `POST /calendar/sync` → `{ connection, changedDays }` ; également chaque nuit (tâche planifiée). `DELETE /calendar/connections/{id}` : lien et créneaux de l'agenda supprimés, la semaine type reprend.
- `GET/PUT /schedule/manual` `{ days: [{ weekday: 1..7, startTime: "HH:MM", endTime: "HH:MM" }] }` (semaine type, heure de Paris) → `{ days, changedDays }`.
- `GET /schedule?from=AAAA-MM-JJ&to=AAAA-MM-JJ` → `{ slots: [{ day, start, end }] }` : créneaux effectifs (agenda connecté, sinon semaine type). Seuls le début et la fin de chaque journée sont stockés, jamais les titres ni les lieux.
- Tout changement de créneau relance les propositions des jours concernés (cahier §3).

## Propositions et recherche
- `GET /proposals?week=AAAA-Www` → `{ week, proposals: [...] }`. La semaine est générée une fois (à la première lecture ou par la tâche du vendredi), puis seulement relancée sur changement d'horaire, de pause ou de profil. Chaque proposition : `{ id, day, direction, time, role, myStatus, rideStatus, seatsTotal, seatsTaken, detourMinutes, driver, passengers }` ; un conducteur sans passager reçoit aussi sa proposition.
- `POST /proposals/{id}/accept` → la proposition à jour. Le trajet passe `confirmed` quand le conducteur et au moins un passager ont accepté. Accepter un trajet où l'on n'est pas (trouvé par « voir d'autres » ou la recherche) crée une **demande de place** (`myStatus: "requested"`) après revérification des places, de l'horaire et du détour (`409 ride_unavailable`) ; sa proposition précédente sur le même créneau est retirée. Le conducteur est prévenu (`ride_requested`) et voit la demande dans ses passagers (prénom, score, détour seulement). Tant qu'il n'a pas répondu, le passager n'accède pas au trajet (`GET /rides/{id}` → 403) : ni nom ni adresse échangés avant l'accord des deux (cahier §4). `POST /proposals/{id}/decline` retire la demande. Passager : le solde disponible doit couvrir le prix maximal du trajet (prix d'un trajet à deux, détour compris), sinon `402 insufficient_funds` (l'app propose de recharger).
- Conducteur : `POST /rides/{id}/requests/{userId}/approve` ou `/reject` → sa proposition à jour ; le passager est prévenu (`request_answered`). Acceptée : le passager est accepté et le trajet confirmé si le conducteur l'avait accepté. Refusée : la paire n'est plus reproposée ce jour-là et une autre voiture est cherchée. `403` hors conducteur, `404` sans demande en attente. Au départ, les demandes restées sans réponse sont refusées.
- `POST /proposals/{id}/decline` → `204` ; seulement avant d'avoir accepté (`409 already_answered` ; l'annulation après acceptation arrive en M5). Un passager qui refuse n'est plus proposé à ce conducteur ce jour-là ; un conducteur qui refuse annule le trajet et ses passagers sont relancés.
- `GET /proposals/{id}/alternatives` → `{ rides: [{ rideId, day, direction, time, seatsLeft, driver }] }` : autres voitures compatibles, classées par détour puis fiabilité (passagers ; liste vide pour un conducteur, les suggestions avec simulation de prix arrivent en M3).
- `GET /search/rides?day=AAAA-MM-JJ&direction=to_campus|from_campus&time=HH:MM` (heure facultative si un créneau existe ce jour-là) : même format ; quota quotidien `app_settings.search.dailyQuota` (`429 search_quota_exceeded`) et limite de débit par IP.
- Avant acceptation mutuelle, les personnes sont représentées par : `userId`, `firstName`, `photoUrl`, `sector` (centre de la cellule de 500 m, arrondi), `reliabilityScore`, `detourMinutes`, `status`. Les schémas de réponse sont stricts : nom de famille, adresse et coordonnées exactes ne peuvent pas sortir de l'API.
- Conducteur uniquement : `GET /rides/{id}/suggestions` → `{ seatsLeft, current: { persons, shareCents, passengerPaysCents } | null, suggestions: [{ person, withinDetourLimit, shareCents, passengerPaysCents }] }` : passagers sans trajet ce jour-là dans ce sens, horaire compatible, y compris ceux écartés car au-delà du détour maximal (`withinDetourLimit: false`), avec le prix par passager simulé (distance estimée, comme le prix actuel). Dix au plus, par détour croissant puis fiabilité. `403 forbidden` hors conducteur, `409 accept_first` tant que le conducteur n'a pas accepté.
- `POST /rides/{id}/suggestions/{userId}/invite` → la proposition du conducteur à jour : la personne reçoit une proposition à accepter (`409 ride_full`, `409 suggestion_unavailable`).

## Trajets
- `GET /rides/{id}` (participant accepté d'un trajet `confirmed`, `in_progress` ou `completed`) → `{ id, day, direction, time, status, role, seatsTotal, distanceM, durationS, routeEstimated, route: [[lat, lon]…], stops, price }`. `403 forbidden` pour toute autre personne (y compris un participant qui n'a pas accepté), `409 ride_not_confirmed` avant la confirmation à deux, `404` si le trajet n'existe pas.
  - `stops` dans l'ordre du trajet : aller = domicile du conducteur, passagers acceptés, campus ; retour = campus, passagers, domicile du conducteur. Chaque arrêt : `{ order, kind: driver|passenger|campus, userId, firstName, lastName, label, lat, lon, eta, isMeetingPoint, pickedUp, presenceValidated, arrived, ended }` (`arrived` : passager arrivé à destination, il paiera à la clôture ; `ended` sans `arrived` : parti avant l'arrivée, il ne paie pas). Le point de rendez-vous remplace l'adresse dans toutes les réponses. Conducteur et passager se sont acceptés : nom de famille et adresse exacte de l'un à l'autre (et pour soi). Entre passagers, pas d'acceptation mutuelle : prénom seulement et, pour un domicile, centre du secteur avec `label` vide (le point de rendez-vous, lieu public, reste exact) ; pour un passager, le tracé est privé de ses points à moins de 500 m d'un domicile masqué.
  - `route` : tracé simplifié ; `routeEstimated: true` si le fournisseur d'itinéraires était indisponible (lignes droites estimées).
  - Plan (ordre des arrêts, tracé, heures de passage, distance) calculé à la confirmation, puis recalculé quand un passager accepte ou change de point de rendez-vous ; aller : arrivée au campus à l'heure cible, retour : départ du campus à l'heure cible.
- `GET /rides/{id}/price` → `{ price }` : `{ estimated: true, totalCostCents, persons, shareCents, commissionCents, passengerPaysCents, driverReceivesCents, youPayCents, youReceiveCents }`, `null` si le conducteur n'a plus de véhicule. Coût = consommation × distance du tracé × `pricing.fuelPriceCentsPerLitre`, partagé entre conducteur et passagers acceptés (part arrondie au centime supérieur), plus `pricing.commissionCentsPerPassenger` pour chaque passager. Le prix final est calculé à la clôture (M4).
- `PUT /rides/{id}/me/pickup` `{ useMeetingPoint, label?, lat?, lon? }` → `204` (passager accepté, trajet pas encore commencé) : à moins de `rides.meetingPointMaxMeters` du domicile (`422 meeting_point_too_far`) ; `useMeetingPoint: false` revient à l'adresse. `403 forbidden` pour le conducteur ou un non-participant, `409 ride_locked` une fois le trajet commencé.
- `GET /rides?status=` : liste des trajets du jour, plus tard (l'app passe par « Ta semaine »).
- `POST /rides/{id}/start` (conducteur accepté, trajet `confirmed`, au plus tôt `rides.startWindowMinutes` avant l'heure du trajet) → `204` : passe en `in_progress`, ouvre le suivi en direct et retient sur le portefeuille de chaque passager accepté son prix maximal (trajet à deux) ; un passager dont le solde ne suffit plus perd sa place (`cancelled`, sans pénalité) et est prévenu (`payment_required`). `403 forbidden` hors conducteur, `409 too_early`, `409 ride_not_confirmed`. Rejoué : sans effet.
- `POST /rides/{id}/participants/{userId}/picked-up` (conducteur, trajet en cours) → `204` : « monté » ; l'arrêt sort de la navigation (`stop_picked_up` diffusé).
- `POST /rides/{id}/presence` (passager) → `{ status: "validated" | "already" }` : la présence est validée si les dernières positions du passager et du conducteur sont à moins de `tracking.presenceRadiusMeters` et que celle du conducteur est vraisemblable (`409 presence_not_confirmed` sinon). Elle est aussi validée automatiquement quand le téléphone du passager reste proche de celui du conducteur pendant au moins 15 s ; la position du conducteur seule ne valide jamais un passager. Une position qu'on n'a pas pu atteindre depuis la dernière position crue à 144 km/h de moyenne (au-delà de 500 m) n'est pas crue. Elle ne déclenche aucun paiement : le passager paie à la clôture, s'il est arrivé. Arrivée : son téléphone, ou une position crue du conducteur après sa prise en charge, à moins de `tracking.arrivalRadiusMeters` de sa destination (`passenger_arrived` diffusé) ; son suivi s'arrête alors (socket fermé en `4410`, reconnexion refusée).
- `POST /rides/{id}/finish` → `204`. **Passager** à bord (présence validée, sinon `409 not_on_board` : il annule sa place) : termine son trajet seulement ; sa part reste due, même avant la destination prévue ; le conducteur est prévenu tout de suite (`passenger_left`, push et socket) ; son suivi s'arrête. **Conducteur** : clôture pour tous (`completed`) ; prix final = coût du tracé ÷ (passagers présents + conducteur), plafonné à la retenue de chacun (le plan est figé au départ ; seul le retrait de passagers peut le raccourcir ; sans tracé calculé, distance estimée comme pour la retenue) ; chaque passager présent paie (arrivé ou descendu avant), les autres retenues sont libérées ; la part du conducteur va sur son compte « en attente » (`pendingCents`) et devient disponible après `wallet.releaseAfterHours` (24 h), sauf litige en attente d'arbitrage ouvert par le payeur ou le conducteur sur ce trajet (tâche planifiée toutes les heures). Un passager jamais validé dont l'heure de prise en charge est passée est `absent` (pénalité) ; sinon `cancelled`, sans pénalité, prévenu (`ride_cancelled`) ; le trajet ne compte comme mené à bien pour le conducteur que si personne n'est resté en attente. Clôture automatique quand le conducteur arrive à destination (à l'aller, ses passagers présents arrivent avec lui), quand tous les passagers ont terminé, ou après `rides.staleAfterHours`. Rejoué : sans effet.

## Navigation (conducteur uniquement)
- `GET /rides/{id}/navigation` (trajet `confirmed` ou `in_progress`) →
```json
{
  "stops": [
    { "order": 1, "kind": "passenger", "userId": "…", "firstName": "Hugo", "label": "12 rue …", "lat": 45.9, "lon": 6.12, "eta": "2026-10-20T07:42:00Z", "pickedUp": false },
    { "order": 2, "kind": "destination", "userId": null, "firstName": null, "label": "Campus d'Annecy", "lat": 45.92, "lon": 6.15, "eta": "…", "pickedUp": false }
  ],
  "links": {
    "googleMaps": "https://www.google.com/maps/dir/?api=1&destination=LAT,LON&waypoints=LAT,LON%7CLAT,LON&travelmode=driving",
    "appleMaps": "https://maps.apple.com/?daddr=LAT,LON+to:LAT,LON&dirflg=d",
    "waze": { "nextStop": "https://waze.com/ul?ll=LAT,LON&navigate=yes" }
  },
  "supportsMultiStop": { "googleMaps": true, "appleMaps": true, "waze": false }
}
```
Les liens portent les arrêts restants (pas encore montés) dans l'ordre, puis la destination (campus à l'aller, domicile du conducteur au retour) ; sans origine, l'application part de la position du téléphone. Ils ne contiennent que des coordonnées. `403` pour tout autre utilisateur.

## Suivi en direct (WebSocket)
`GET /ws/rides/{rideId}?token=<jwt>` (upgrade) ; le jeton n'est jamais journalisé. Messages JSON :
- Client → serveur : `{ "type": "position", "lat": 0, "lon": 0, "accuracy": 8, "speed": 12.5, "ts": "ISO-8601" }` ; une position toutes les 2 s au plus (les autres sont ignorées).
- Serveur → client : `{ "type": "ready", "role": "driver" | "passenger" }` (abonné ; suivi de la dernière position connue du conducteur), `{ "type": "position", "userId", "lat", "lon", "ts" }`, `{ "type": "eta", "userId", "eta" }`, `{ "type": "stop_picked_up", "userId" }`, `{ "type": "presence_validated", "userId" }` (au passager et au conducteur), `{ "type": "passenger_arrived", "userId" }`, `{ "type": "passenger_left", "userId" }` (au conducteur), `{ "type": "ride_status", "status": "in_progress" | "completed" }`.
- Diffusion : le passager reçoit la position du conducteur et son heure de passage ; le conducteur reçoit celles des passagers pas encore montés ; jamais d'un passager à un autre.
- Fermeture : `4401` jeton invalide ou expiré (reconnexion avec un jeton renouvelé), `4403` pas participant accepté, `4408` remplacé par une connexion plus récente de la même personne (une seule par trajet), `4409` trajet pas en cours, `4410` trajet clôturé, ou terminé pour ce passager. Positions gardées en mémoire, trace d'un point toutes les 30 s pour les litiges, supprimée après `tracking.traceRetentionDays`.

## Portefeuille et paiements
- `GET /wallet` → `{ balanceCents, heldCents, pendingCents, history: [{ kind, amountCents, rideId, createdAt }] }` (`pendingCents` : parts reçues, versées après le délai de signalement) (50 dernières opérations, retenues exclues).
- `POST /wallet/topups` `{ amountCents }` avec l'en-tête `Idempotency-Key` (8 à 100 caractères) → `201 { status, wallet }` ; minimum `app_settings.wallet.minTopupCents` (`400 topup_too_small`), refus du prestataire `402 topup_failed`. La même clé ne recharge qu'une fois. Fournisseur factice (`PAYMENT_PROVIDER=fake`, refusé en production) : recharge immédiate ; prestataire réel, session de paiement et webhook : M4b.
- Registre `wallet_ledger` en écriture seule (déclencheur en base) ; chaque opération est équilibrée (somme nulle) et idempotente. Comptes : `user:<id>`, `held:<id>`, `platform:commission`, `provider:clearing`.
- Paiement à la clôture, pour chaque passager présent et arrivé : il paie le prix final plus la commission depuis sa retenue (le reste est libéré), le conducteur reçoit la part, Uni-Moov la commission. Jamais de solde négatif.
- `POST /wallet/payouts` `{ amountCents, iban, holderName }` avec l'en-tête `Idempotency-Key` → `201` portefeuille à jour : minimum `wallet.minPayoutCents` (`400 payout_too_small`), IBAN contrôlé (mod 97, `400 iban_invalid`), solde disponible (`409 insufficient_funds`), un par semaine (`429 payout_too_soon`), refus du prestataire `402 payout_failed`. L'IBAN est transmis au prestataire et jamais stocké (4 derniers caractères seulement). Le débit est enregistré (retrait `pending`) avant l'appel au prestataire : un refus le recrédite (`refund`, retrait `failed`, la semaine n'est pas consommée) ; sans réponse, le retrait reste `pending` et débité, à rapprocher. Même clé en parallèle : un seul virement. Limite : 5 par heure.
- `GET /wallet/payouts`, `POST /webhooks/payments` : M4b.
- Montants toujours en centimes (entiers).

## Messagerie (cahier §6)
- `GET /conversations` → `{ conversations: [{ id, kind: direct|group|ride, title, rideId, archived, members: [{ userId, firstName, photoUrl }], unread, lastMessage }] }`, la plus récente d'abord. Prénom et photo seulement, jamais le nom de famille.
- `GET /contacts` : personnes croisées sur un trajet (proposé ou confirmé), seules joignables.
- `POST /conversations` `{ kind: "direct", memberIds: [id] }` (réutilise la conversation existante de la paire) ou `{ kind: "group", title, memberIds }` (au plus `chat.maxGroupMembers`) → `201`. `403 not_a_contact` si une personne n'a jamais été croisée.
- `GET /conversations/{id}` ; `GET /conversations/{id}/messages?before=<iso>&limit=50` (du plus récent au plus ancien) ; `POST /conversations/{id}/messages` `{ body }` (1 à 2000 caractères, 30 par minute) → `201` ; `POST /conversations/{id}/read` ; `DELETE /conversations/{id}/members/me` (groupe seulement, `409 cannot_leave` sinon).
- Non-membre : `404` sur toute conversation, sans révéler son existence.
- Chat de trajet : `GET /rides/{id}/conversation`. Créé à la confirmation avec les personnes acceptées, membres mis à jour à chaque acceptation ou annulation. Fin ou annulation du trajet : lecture seule (`archived: true`, `409 conversation_archived` à l'envoi) après `chat.rideArchiveDays`, puis supprimé avec ses messages `chat.rideDeleteDays` plus tard (tâche quotidienne).
- Temps réel : `GET /ws/me?token=<jwt>` (socket utilisateur, plusieurs appareils) ; le serveur envoie `{ type: "ready" }` puis `{ type: "message", message }`. Fermeture `4401` sans jeton valide.

## Annulations (cahier §8)
- `GET /rides/{id}/cancellation` → `{ role, tier }` : palier de pénalité si la personne annule maintenant (`early`, `medium`, `late`, selon `reliability.penalties`). `409 not_accepted` si elle n'a pas accepté (c'est alors un refus, `POST /proposals/{id}/decline`).
- `POST /rides/{id}/cancel` → `{ tier }`, avant le départ ; pendant le trajet, seulement pour un passager pas encore à bord (présence non validée) : pas de remplaçant, suivi coupé, retenue libérée à la clôture. Pénalité au score de la personne qui annule, notification immédiate des autres participants acceptés (`ride_cancelled`). Passager : sa place est proposée au meilleur passager disponible dans le détour du conducteur ; plus aucun passager accepté, le trajet redevient `proposed`. Conducteur : trajet `cancelled`, chaque passager reçoit une autre proposition si possible (`replacement_proposed`). Pas de pénalité pour les passagers d'un conducteur qui annule.

## Confiance (cahier §7)
- `GET /rides/{id}/ratings` → `{ open, closesAt, people: [{ userId, firstName, photoUrl, role, stars }] }` : trajet terminé, conducteur ↔ passagers dont la présence est validée, jamais entre passagers. `403` pour un absent ou un tiers.
- `POST /rides/{id}/ratings` `{ ratedUserId, stars }` (1 à 5, sans commentaire) → `204`. Une fois par personne (`409 already_rated`), pendant `ratings.windowDays` après la fin (`409 rating_closed`).
- `GET /me/reliability` → `{ score, windowDays, completedRides, cancellations: { early, medium, late }, noShows, ratingsCount, averageStars, events: [{ id, kind, rideId, day, createdAt, disputeReason }] }`. `disputeReason` non nul : l'entrée est encore contestable.
- Score : moyenne bayésienne du comportement (trajets menés à bien face aux pénalités) et des notes, sur `reliability.windowDays` ; il ne sert qu'à classer dans le matching (détour + `matching.reliabilityWeightSeconds` × (1 − score)), jamais à exclure.

## Litiges (cahier §10)
- `POST /rides/{id}/disputes` `{ reason, message? }` → `201 { id, rideId, reason, level, decision, explanation, createdAt, escalatedAt }`. Motifs : `cancellation_penalty`, `marked_absent`, `payment`, `driver_issue`, `other`. Niveau 1 tranché sur les horodatages du serveur (`upheld`, `corrected` avec correction du score) ; sinon niveau 2 (`escalated`), mail à `support.email`. Un litige par motif et par trajet (`409 dispute_exists`), pendant `disputes.windowDays` (`409 dispute_closed`).
- `POST /disputes/{id}/escalate` `{ message? }` : désaccord avec la décision, passage au niveau 2 (idempotent).
- `GET /rides/{id}/disputes` : mes litiges sur ce trajet. Un passager compté absent garde l'accès en lecture au trajet clôturé (`myStatus: "absent"` dans `GET /rides/{id}`).

## Signalements
- `POST /reports` `{ targetUserId, reason, message? }` → `201 { id }` ; motifs `dangerous_driving`, `inappropriate_behaviour`, `fake_profile`, `other`. Seulement une personne croisée sur un trajet (sinon `404`, comme une personne inconnue), `reports.dailyLimit` par jour (`429 report_limit`). Transmis à l'équipe par mail, jamais à la personne signalée.

## Notifications (cahier §11)
- `POST /devices` `{ platform: android|ios, pushToken }` → `204` (le jeton appartient au dernier compte connecté sur l'appareil) ; `DELETE /devices` `{ pushToken }` à la déconnexion.
- `GET /me/notification-preferences` → `{ match, rideUpdate, rideReminder, chat }`, tout à `true` par défaut ; `PUT` avec une partie des clés.
- Événements et catégorie : `proposals_ready` et `replacement_proposed` (match), `ride_cancelled`, `ride_requested`, `request_answered`, `payment_required` (solde insuffisant au départ), `passenger_left` (rideUpdate), `ride_reminder` (rideReminder, `notifications.reminderMinutes` avant le départ, un seul par personne et par trajet), `chat_message` (chat, seulement aux membres non connectés au socket).
- Contenu du push : titre et phrase courte, jamais le texte d'un message ni une adresse ; `data` ne porte que `type` et un identifiant (`rideId`, `conversationId`, `week`) pour ouvrir le bon écran.
- Envoi par `PushProvider` : FCM HTTP v1 (`PUSH_PROVIDER=fcm`, clé du compte de service dans `FCM_SERVICE_ACCOUNT_FILE`) ou journal en développement. Un jeton refusé par FCM est supprimé.
